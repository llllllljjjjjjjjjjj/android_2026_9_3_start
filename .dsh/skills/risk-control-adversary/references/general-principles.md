# 泛化风控对抗经验库（L1 基础原理层）

> 本库是**三级分层知识库的 L1 基础原理层**：通用风控规律与检测原理（E- 成功经验 / F- 失败经验），跨项目复用。上层：L2 场景方案层（references/scenarios/）、L3 项目定制层（references/projects/）。
> 本库由三部分组成：**§0 使用与维护规则**（写入/检索前必读）→ **条目索引** → **条目正文**。格式契约（字段/证据/置信度/标签/生命周期全量定义）见 templates.md §3、§6、§7。
> 编号递增、只增不覆盖：**核心原理完全重合的知识不新增编号**——判定粒度、评审流程与合并/补充格式见 §0.3（追加前先走评审流程，判定新增还是融合，原内容涵盖则不动）。
> **请求策略与行为画像类是最高优先级资产**——风控对抗的主战场是单设备行为，不是算法。
> **归属约定（交叉引用）**：本库维护全部风控知识条目的「检测原理 + 对抗思路 + 证据」；签名/参数加密算法细节→protocol-signature-reverser，环境检测/反 Frida 手法→android-dynamic，传输指纹手法→android-recon fp_stack——落地手法一律在条目「落地工具」字段交叉引用专项 skill 具体章节，不重复展开。

## §0 使用与维护规则（写入 / 检索前必读）

### 0.1 证据等级（五档 + 数值阈值）

证据等级回答「**有没有经过验证**」，由两个正交数字决定：**复现次数 R**（受控条件下重复成功的次数）与**样本量 N**（参与验证的账号 × IP/设备数 × 独立条件数）。样本量记录格式：`<账号数>账号 × <IP/设备数> × <复现次数>`；未记录写 `-（未记录）`。

| 等级 | 定义 | 数值阈值（R × N） | 升级路径 |
|------|------|--------------------|----------|
| 已实证 | 本方案实测复现，可重复 | R ≥ 3 且 N ≥ 2（跨账号/IP/设备/时段 ≥2 种独立条件） | — |
| 大样本 | 多次跨条件验证，可支撑统计结论 | R ≥ 5 且 N ≥ 10，且跨 ≥2 平台/时段 | 已实证升级 |
| 小样本 | 单次或少次实测 | 1 ≤ R ≤ 2，或 N < 2 | 补测至 R≥3 且 N≥2 → 已实证 |
| 推测 | 有线索（情报/静态分析/单点观察），未做受控验证 | R = 0，有线索 | 受控复现 1 次 → 小样本 |
| 未知 | 无任何证据 | 无线索 | 获线索 → 推测 |

- **中间样本区间衔接**：小样本 = 1-2 次复现或单条件；满 3 次复现且跨 2 条件即升「已实证」，无空白档。
- 升级必须跑 SKILL.md A3.5 验证闭环（跨账号/IP/设备 ≥3 次 + 7 天灰度 + 对照组），达标后在条目「版本」追加记录（§0.8）。
- 降级同理：失效条件出现（§0.8）时降级并标注原因。

### 0.2 置信度（分级依据 + 与证据等级的对应）

置信度回答「**信源可靠吗**」——独立于证据等级的第二个轴，不随证据等级自动升降：

| 置信度 | 分级依据 |
|--------|---------|
| 高 | 实测抓包 / 项目实测 / 官方文档，可直接指导决策 |
| 中 | 技术社区 / 专业书籍，需交叉验证 |
| 低 | 自媒体 / 单源 / 信息陈旧，仅作线索 |

**与证据等级的对应逻辑**（正交组合，不是推导关系）：

| 组合 | 判定 |
|------|------|
| 已实证 × 高 | 项目实测复现（最可靠），如 E-13 / E-26 |
| 已实证 × 中/低 | 实测复现但信源弱 → 复核来源，置信度不因实测自动升档 |
| 推测 × 高 | 官方文档明确声明但未实测 → 强线索，需补受控验证 |
| 推测 × 低 | 自媒体线索（如 E-15~E-19），作为调研起点 |
| 可疑组合 | 已实证 × 低 = 信源与实测矛盾，先复核证据再采信 |

**置信度升级路径**：低 →（多源交叉一致）中 →（实测/官方）高；降级同理反向。

### 0.3 核心原理重合判定（判定粒度 / 评审流程 / 合并与补充格式）

**判定对象（粒度）**：E 条目 = 「检测原理 + 对抗思路」二元组；F 条目 = 「触发条件 + 根因」二元组。**类型或角度相同不算重合，二元组相同才算**。

**判定结果与处置**：

| 判定 | 条件 | 处置 |
|------|------|------|
| 完全重合 | 二元组均相同 | 不新增编号，原条目下追加补充行（见下） |
| 部分重合 | 检测原理同但对抗思路不同，或反之 | 优先并入原条目追加「变体」；思路差异大无法容纳 → 新增编号并双向标注 `关联: E-xx（互补）` |
| 不重合 | 二元组均不同 | 新增编号 |

**评审流程（写入前 3 步，防冗余与误判）**：
1. **索引初筛**：按「类型 + 标签领域/主题」在条目索引筛候选（检索路径见 §0.7）；
2. **精读比对**：读候选条目全文，比对二元组是否相同/部分相同；
3. **落库留痕**：判定「追加 / 变体 / 新增」并落库；涉及修正他人条目时在「版本」与「失效状态」字段留痕（§0.8）。

**合并与补充格式**（只增不覆盖，原文不动）：
- 追加新场景/平台/工具：`- 补充(v1.1, YYYY-MM-DD): <新场景/平台/工具/样本>`
- 追加认知变化：`- 修正(v1.2, YYYY-MM-DD): <旧认知> → <新认知>`
- 追加后同步：样本量（累加新数据）、失效状态（如需）、索引表「版本」列 +0.1。

### 0.4 沉淀准入（L3 项目经验 → L1 通用原理）与评审流程

**准入标准（4 条全满足才允许沉淀）**：
1. **可泛化**：结论能抽象为「<对象>的<规律>」，不含项目专有名词（接口名/字段名/具体数值）；
2. **跨项目价值**：≥1 个其它项目/场景可复用，或能修正已有 L1 认知；
3. **证据门槛**：L3 记录中证据等级 ≥ 小样本（有实测）；纯推测结论只做「待验证」登记，不进 L1；
4. **非排除项**：不是项目专属细节、不是未验证即放弃的临时结论、不与现有 L1 完全重合。

**评审流程（沉淀时 3 步）**：
1. **抽象化检查**：把 L3 具体结论改写为通用表述（对照准入 1）；
2. **冲突检查**：对照索引按 §0.3 判定「合并 / 变体 / 新增」；
3. **登记**：新增编号在 L3 记录「泛化提炼」节登记（templates.md §2）；合并则在 L3 记录注明「已并入 E-xx/F-xx」。

### 0.5 落地适配（L1 → L2 → L3）与跨层级引用标注

**自上而下落地**：
- **L1 → L2**：场景方案 = 该场景涉及的 L1 条目组合 + 参数化默认值 + 验证顺序，引用格式 `依据 E-xx/E-yy（L1）`；
- **L2 → L3**：项目方案 = 套用场景方案模板 + 项目实测参数替换（节奏对拍/接口清单/证据落地）+ 项目特有细节；
- 每层下钻都做**适配检查**：平台差异（§0.10）、节奏参数对拍、验证闭环（A3.5）。

**跨层级引用标注规范**：
- 引用一律带层级后缀：`（L1）` / `（L2）` / `（L3）`；
- L1 条目「来源」字段中的 `projects/xxx 日期` 即对 L3 的反向引用（元信息，不算依赖）；
- 遵守分层规则：上层复用下层，下层不依赖上层——L1 正文不得出现「某项目实测」以外的项目结论。

### 0.6 标签体系（领域 - 平台 - 难度 - 主题 四级）

标签是检索主入口，**固定四级、固定顺序、`/` 分隔**：`领域/平台/难度/主题…`（词表、命名规范与新增/同义合并规则见 templates.md §6）：
- **领域**（必选 1）：六维 + 扩展——签名 / 参数加密 / 设备指纹 / 环境检测 / 请求策略与行为画像 / 业务规则风控 / 防御侧 / 其他；
- **平台**（必选 1）：Android / iOS / Web / 小程序 / 跨平台——取实测/验证平台；原理与客户端平台无关（行为层/IP 层）或已在 ≥2 端验证才用「跨平台」，并写「平台适配」字段（§0.10）；
- **难度**（必选 1）：入门 / 进阶 / 高级；
- **主题**（1-3 个，受控词表）：节奏 / 频控 / IP代理 / 出口治理 / 数据中心 / 灰名单 / 隧道 / 蜜罐 / 数据校验 / 埋点 / 心跳 / 状态机 / 行为熵 / 时空轨迹 / 关联图谱 / 去关联 / 行为路径 / 指纹提取 / 自洽 / 硬件 / 传感器 / TLS / TCP/IP栈 / HTTP头 / UA / 模拟器 / 沙箱 / 多开 / Root / 框架 / Hook / 反Frida / ELF / 注入时机 / 签名比对 / 路径规则 / 封禁 / 接口分层 / 采集面 / 灰度 / 监控 / UI自动化 / 序列 / 参数完整性 …

示例：`请求策略与行为画像/Android/进阶/IP代理/数据中心/路径规则`（E-26）。

### 0.7 标准检索路径与排查指引

**检索路径（4 步）**：① 定平台（Android/iOS/Web/跨平台）→ ② 定领域（六维）→ ③ 定难度 → ④ 主题词过滤（≤3 个）→ 读命中条目正文（含「关联」跳转）。
示例：给列表接口采集找策略 → 平台 Android → 领域 请求策略与行为画像 → 难度 进阶 → 主题 IP代理/路径规则 → 命中 E-26 / F-02 / F-03。

**排查指引（检索无结果时按序自查）**：
1. 平台词用错？单端实测但原理通用时可能标「跨平台」或反之为实测端；
2. 主题词过细？换上位词（「数据中心」→「IP代理」）；
3. 是否已并入其它条目？查版本 >v1.0 条目的「补充」行（§0.3 合并记录）；
4. 是否已作废？查索引「状态」列（已作废不参与检索）；
5. 以上皆否 → 知识盲区：触发 SKILL.md A1.5 搜索补录，来源注明公开情报。

### 0.8 生命周期（失效标记 / 版本号 / 冲突仲裁）

**失效状态**（三态，索引「状态」列同步）：

| 状态 | 含义 | 处置 |
|------|------|------|
| 生效 | 当前可用 | 正常参与检索 |
| 待验证 | 证据 ≤ 推测，或有失效风险信号 | 复用前先验证；下次命中时触发验证 |
| 已作废 | 原理被证伪 / 方案被平台升级淘汰 / 来源失实 | 不参与检索，正文保留历史；标注 `已作废（原因: …，日期: YYYY-MM-DD，替代: E-xx/F-xx）` |

> 与专项 skill 的关系是**交叉引用不是移交**：本库是「检测原理 + 对抗思路 + 证据」的唯一维护者；专项 skill 是「具体操作步骤」的落点。条目「落地工具」字段写专项 skill 具体章节作交叉引用，不在此重复展开手法。

**版本号与更新标识**：条目版本 v1.0 起，每次「补充 / 修正 / 证据升降级」+0.1；追加内容用 `- 补充(v1.x, 日期): …` 行、认知变化用 `- 修正(v1.x, 日期): 旧 → 新` 行——**原文永不改写，只增行**（呼应只增不覆盖）。

**冲突条目仲裁规则**（同原理不同结论 / E 与 F 矛盾 / 来源冲突时）：
1. **优先级**：证据等级 已实证 > 大样本 > 小样本 > 推测 > 未知；同级比信源：实测项目 > 官方文档 > 技术社区 > 自媒体；再同级取时间新者（记录版本）；
2. **处置**：高者保留为「当前认知」并保持「生效」；低者标记「已作废（被 E-xx/F-xx 修正）」或降级「待验证」并备注依据；
3. **留痕**：仲裁日期、双方编号、依据写入被降级条目的「已作废/待验证」标注。

### 0.9 F 类失败经验价值化（F → E 转化 / 影响分级 / 使用方式）

**F → E 转化机制**：F 条目的「规避方案」即 E 条目的候选原理。转化条件：规避方案在 ≥2 项目/场景复现成功（证据等级 ≥ 已实证）。
**验证流程（4 步）**：① 从 F 的「规避方案」抽象出正向规律（去除项目专有名词）→ ② 按 E 条目标准补「检测原理/对抗思路/落地工具」→ ③ 在下一项目应用验证（R≥3 且 N≥2）→ ④ 达标后新增 E 编号或并入已有 E；F 条目保留（历史价值），在「转化」字段登记 `转化: 已转化 → E-xx`；未达标登记 `转化: 候选（待跨项目复现）`。

**影响分级**（F 条目必填「影响等级」）：致命（方案整体失效 / 资源被拉黑，恢复成本高）/ 严重（主数据面不通，需换资源）/ 一般（局部影响，参数调整可恢复）。

**适用风控版本与失效条件**（F 条目必填）：
- 「适用风控版本」：该失败经验针对的风控体系/平台版本（如 `dzdp WAF「出口 IP×路径」规则 2026-08`）；风控升级后需复核；
- 「失效条件」：什么情况下该失败经验不再成立（平台换风控厂商 / 规则调整 / 检测维度变化）。

**F 条目使用方式**：
- **风险预判**：新方案设计时按索引扫同类目标/手段的 F 条目，把「触发条件」转成方案「失败模式与坑」清单（templates.md §1），逐条给预防；
- **方案校验**：把 F 的「失败特征」作为方案的**负面信号清单**——验证期出现任一信号即判定进入风险态，触发熔断（对照 E-26 / F-02 的 openresty 403 信号）。

### 0.10 跨平台适配说明（平台 = 跨平台的条目必读）

「平台适配」字段 = 该原理在 Android / Web / iOS 各端的差异与适用边界（**指导性判断，非实测数据，不参与证据等级评定**）。无差异时写「三端通用」。标注守则：
- 只写**技术原理层面的确定差异**（如传感器采集 iOS 受限、Canvas 指纹仅 Web 端），不写未经证实的平台结论；
- 某端不适用时写「该端不适用 / 弱化」，并给替代手段。

### 0.11 落地执行约定（「本 skill」指代与策略 → 脚本）

- 「**本 skill**」= risk-control-adversary 的**方法论 + references/ 知识库**，不是脚本库；条目「落地工具」字段中的「本 skill 策略 → 脚本实现」指：按 SKILL.md A3 请求策略清单 + templates.md §7 交付模板，产出**脚本参数配置表**（每个策略维度映射到脚本参数，含默认值/变异范围/熔断信号）。
- **交付标准**：① 每条策略必须能映射到脚本参数；② 参数必须有默认值与变异范围；③ 每个熔断信号有处置动作；④ 按 A3.5 验证闭环跑通后才算交付。

### E-02 拟人化节奏与频控对拍 ⭐

- 类型: 请求策略与行为画像
- 检测原理: 固定间隔/均匀节奏/高频批量是脚本请求最显著的时间特征；风控侧对单设备做时间序列画像
- 对抗思路: 拟人化随机间隔（有节拍、不完全随机）+ 贴频控阈值设计批量大小 + dry-streak 跳带（连续无结果时主动跳过一段，模拟用户失去兴趣）+ 退避策略；先用实测节奏跑通（如 dy 翻页 0.8s 间隔无风控），再逐步提速对拍阈值
- 落地工具: 采集脚本节奏参数（本 skill 策略 → 脚本，见 templates.md §7）
- 适用平台: Android（实测基线；原理通用，其它端按同法对拍）
- 适用范围: 高频批量采集、翻页/列表接口；不适用：实时性要求高的场景（需先对拍）
- 操作边界: 提速以「连续 200 且无 403/验证码/蜜罐」为上限，留 30-50% 余量不贴死阈值；单设备频率预算与作息时段绑定
- 异常判定: 出现 429/403/验证码/返蜜罐 → 立即回退上一档节奏并记录阈值；连续 2 档回退仍异常 → 切换 IP/账号（对照 F-02 熔断）
- 关键步骤: ① 实测当前节奏（如 0.8s 无风控）→ ② 按 1.5-2× 间隔保守起步 → ③ 逐档提速对拍（每档稳定 ≥24h）→ ④ 锁定阈值后注入随机变异因子
- 证据等级: 已实证（样本量: dy 单项目实测 0.8s 翻页间隔，跨时段未系统验证）

### E-04 IP 出口治理与黑名单意识 ⭐

- 类型: 请求策略与行为画像
- 检测原理: 按来源 IP 统计频率/总量/间隔，识别代理池、VPN、黑产 IP 黑名单、同 IP 多账号并发；处置从 403/429 到限流到返蜜罐数据逐级变化
- 对抗思路: 换 IP 前先评估 IP 质量——公用代理 IP 大概率已被平台标记，黑名单不随换 IP 消失；猫池（多 SIM 卡动态 IP）质量高但成本高；保持 IP-设备-账号三者归属一致，避免同 IP 多账号/同账号多 IP 的交叉污染

### E-27 风控柔性降级伪装的识别

- 类型: 业务规则风控
- 检测原理: 风控平台对已封禁账号采用**分层处置**：直接调用核心功能接口返回明确封禁码（如 2999「功能已禁用」），但查询/摘要类接口把账号状态字段降级（如 `validStatus=false`），客户端据此显示「本学期还未开始」「当前不可用」等模糊提示，掩盖真实封禁

- 落地工具: 本 skill 策略 → 脚本实现（封禁判据状态机：以目标功能主接口返回码为准，软提示只作参考信号）

- 操作边界: 只做状态识别与判据交叉验证，不绕过封禁；识别后应停止该账号请求，换干净资源

### E-30 降级分级识别（软降级 vs 硬拒绝）

### E-31 风控签名位于 native 层（跨层观测不可互否）

- 类型: 签名
- 检测原理: 强签名平台的签名头由 native 层（SO）在发送前注入传输流，Java 层完全不可见；因此在 Java 层 hook 签名相关方法会得到「零调用」的假象
- 对抗思路: 以**传输层实际字节**为唯一权威证据——抓 TLS 请求头（HTTP/2 需 HPACK+Huffman 解码）或抓 native 发送函数，不依赖单一层次的 hook 命中
- 落地工具: 本项目 `scripts/cap_h2_headers.py`（SSL_write → HTTP/2 帧 → HPACK → Huffman 全解码）；签名算法还原交 protocol-signature-reverser
- 适用平台: Android
- 适用范围: 存在 native 签名 SDK 的 App；纯 Java 签名的场景不适用
- 操作边界: 不因单层零命中就断言机制不存在；跨层结论冲突时以传输层字节为准
- 异常判定: Java 层 hook 零命中但请求头存在签名 → 即为本条适用信号
- 关键步骤: 1. hook 传输层取原始请求头 2. 解码协议封装（H2/TLS） 3. 与 Java 层观测交叉验证

### F-06 协议直发缺 native 签名头致硬拒绝

- 类型: 失败经验
- 触发条件: 用自己的 HTTP 客户端直发业务请求（URL/body 逐字复用真实抓包），但未携带 native 层注入的签名头

### F-07 高频 hook 点与多脚本加载致进程崩溃

- 类型: 失败经验
- 触发条件: ① hook 高频调用的集合方法（如 HashMap.put）并在回调内构造 Java 对象；② 向同一进程加载多个 Frida 脚本
