八神链路：试错到跑通全过程
阶段 1：入口定位——「找到的那个函数，不是签名生成器」
从 jadx/静态出发，锁定 libsscronet.so 0x4127ac（x-argus/x-gorgon 等字符串 xref 全在这）。hook10 抓到完整八神后，hook15 追写入链，把目标锁定在 sub_47A31C——反汇编一看：它不是八神生成器，是 ttnet 流量控制入口（处理 x-ttnet-origin-url 等头）。

转折点：47A31C 内部有一行 BLR X23(X0=str1, X1=str2)，X23 来自全局 qword_5FFE80，返回 char*。签名是从这个全局回调指针出去的，不是这个函数自己生成的。hook16 读 [qword_5FFE80] 的运行时值 → libmetasec_ml.so+0x28065c，真正的八神生成器。

教训：调用链上"写签名头的地方"≠"生成签名的地方"，BLR 间接调用要追指针值。

阶段 2：静态深挖——28065c 是 MS SDK 不是抖音自研
dump rwxp 页 + bss 页合并成 dec.so 丢进 IDA（9.2 headless 批量反汇编）。解出：

28065c 的输入消息构造：msg = headers + "\r\nURL\r\n" + url（常量在 0x3E4F98）
内部编排：264E3C(out, mode, msg) 两遍 → 274C60 → free
全局字符串区出卖身份：[DouYin] RunPreInitHooks、https://mssdk.bytedance.com、http_sign_gen_all → libmetasec_ml = 字节跳动 MS SDK
274C60 区发现 syscall 包装（syscall 号 +0xE9 偏移反静态）+ 11-dword 滚动 checksum 反 hook → 划定"勿 hook 区"
教训：没有直接啃 28065c 的每一行，而是先看全局数据区——字符串是混淆代码里最诚实的东西。

阶段 3：动态观测——frida CLI 跑不起来
写好 hook20（三层观测：28065c / 264E3C / 274C60），frida CLI 直接跑：exit 1，零输出，试了 -o 重定向和 --debug 都失败。

解决：翻 transcript 发现之前 hook15-19 全走 run_hook_attach.py（Python attach 运行器）——frida CLI 在 stdin 非 TTY 时立即退出。改用 Python runner 后成功，拿到 264E3C 的 msg 格式（service\r\n9999\r\nmethod\r\n1\r\npayload_md5\r\n<md5>）、out 缓冲写指针、两个固定 VMP 入口。

阶段 4：RPC oracle——连踩 3 个坑才跑通
第 1 坑：App 从 frida 进程表消失了。get_process(pkg) 报 ProcessNotFoundError，但 adb 看到进程活着——App 运行一段时间后反枚举（MS SDK 的 275208 反检测监控区）。解：adb shell pidof 拿 pid 直连 attach(pid)。

第 2 坑：RPC 方法名找不到。get_base 报错，改 camelCase getBase 还是报错——最后发现 frida 16.5.7 的 Python 绑定把属性名 lower() 之后查找，JS 端方法必须全小写（oracle/oraclebatch）。这个坑用 dir(sc.exports_sync) 打印代理属性 + 逐个试才定位。

第 3 坑：空 URL 返回 NULL → Python 侧 NoneType 崩溃。App 没崩（28065c 有内部防御），JS 侧加 r.isNull() 防御、Python 侧加 (r.get("o") or "") 防御后全量跑通。

顺带发现分支行为：oracle('https://x/', ...) 只返回 X-Neptune（第 9 个头，新发现），对照实验确认分支条件 = URL 有无完整 query，与 headers 无关。

阶段 5：差分分析——两个被推翻的假设
假假设 1：Gorgon 上下文"每 10 次签名轮换"。G2/G3 批内切换点都在 idx 0→1、10→11，看着像计数驱动。25 次同 URL 慢速实验（每次 ~100ms 往返）切换点变成 3,6,13,17,23——不规则。sleep 控制实验：0.1s 不切、0.25s 切、0.4s 不切……最终定性：~0.5-0.6s 时间轮换，由 App 后台网络活动驱动（批内 μs 级间隔来不及轮换才显得像计数）。

假假设 2：Argus 第 2 字节是"神秘字段"。低字节完美跟随 Khronos（c8/c9/ca/cb），但 byte1（0x11/0x12/0x13）一度对不上——后来发现是自己十六进制手算错了。用程序重新换算：base64(LE32(ts)) 对 8 个历史点 + 12 个跨秒点全吻合，SF-012 通过。

Gorgon 输入范围用 6 变体一次性锁定：query 键/值都参与、path/scheme/fragment 全排除——与静态分析的 282020 strchr('?'/'#') 提取器互相印证。md5/crc32/sha256 全不匹配 → keyed hash（轮换密钥），离线复现死路 → 策略落地为在线 oracle。
